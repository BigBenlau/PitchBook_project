# Part6: Investor Capability Formal Pipeline

## Objective

Part6 classifies the formal Part5-to-Part6 investor universe for six investor
capabilities:

- `otc_trading`
- `algorithm_trading`
- `market_making`
- `execution_services`
- `defi`
- `sub_fund`

Canonical input:

- `part5_to_part6/output/part6_investor_input.csv`
- `part5_to_part6/output/part6_batches/batch_*.jsonl`

Canonical final outputs:

- `part6_analyse_investor_capabilities/agent_runs/crypto_investor/classifier_results.csv`
- `part6_analyse_investor_capabilities/agent_runs/crypto_investor/results.csv`
- `part6_analyse_investor_capabilities/agent_runs/crypto_investor/needs_manual_review.csv`

Each input investor row must map to exactly one classifier row and exactly one
result row. Part6 must not create extra investor rows, merge unrelated
PitchBook investor rows, or drop input rows. The final row invariant is one
output row per input row, in the exact input order. Multi-value fields must be
stored as valid JSON list strings where the schema requires JSON lists.

The current approved input has 10,353 investors and 346 JSONL batches. If the
bridge is rebuilt, the generated bridge summary and verifier become the source
for the expected row count.

## Formal Inclusion Rule

The only official Part6 universe is the investor universe generated by
`part5_to_part6/scripts/1_build_part6_investor_input.py` from formal Part5
token-company results. Historical branch outputs, old delta folders, removed
investors, and previous full-run outputs are not active Part6 inputs.

The inherited upstream rule is:

- include a company only when Part5 has a non-empty formal `token_results`
  JSON list;
- include tokens only for officially recognized founding, co-founding, or
  original founding organizations of the blockchain/protocol ecosystem;
- require strong, direct, stable evidence from official, primary, or trusted
  sources;
- exclude ordinary investors, advisors, partners, vendors, customers,
  portfolio-only exposure, grants, ecosystem mentions, and generic token
  references from Part5 token-company inclusion.

Part6 does not decide whether an investor belongs in the universe. It must
preserve every canonical input investor row and classify that row under the six
capability definitions below.

Capability `yes` decisions require current, direct, source-backed evidence.
Use this source hierarchy:

1. current official source;
2. current official documents, filings, product/service pages, portfolio pages,
   or backer pages;
3. current trusted third-party databases;
4. stale databases, ordinary news, social media, and local PitchBook input.

Use ordinary news, social media, and local PitchBook only as search or
disambiguation context. They cannot directly support a capability `yes`.
Current official sources win over conflicting database or news evidence.
Historical, bankrupt, liquidated, stopped, pivoted-away, removed, or
discontinued evidence does not support `yes`.

## Worker Workflow

Workers must read:

- `part6_analyse_investor_capabilities/Plan.md`
- `part6_analyse_investor_capabilities/agent_prompt_template.md`
- the assigned `batch_*.jsonl`
- the prepared `tasks.jsonl`

Workers must:

- write one classifier row and one result row for every assigned task row;
- write rows incrementally as each investor is completed, not only at batch end;
- copy `task_index`, `investor_id`, `investor_name`, `normalized_domain`, and
  `primary_investor_type` exactly from the top-level JSONL task fields;
- keep output schemas unchanged and write only to the active attempt CSVs
  provided by the runtime wrapper;
- use `gpt-5.5` with `xhigh` reasoning when launched by the runtime harness.

Allowed `search_tier` values:

- `full`
- `light`
- `skip_candidate`

Routing rules:

- Use `full` for explicit OTC, market making, trading, liquidity, execution,
  brokerage, quant/systematic/HFT, DeFi trading/protocol operation, exchange,
  operating-company, or parent/child fund-structure signals.
- Use `light` for weak or ambiguous crypto/Web3/fintech/investor/fund signals
  that still require bounded confirmation.
- Use `skip_candidate` only when the row is clearly and completely unrelated to
  crypto/Web3, financial services, investing/funds, trading/execution/liquidity,
  DeFi, and parent/sub-fund structure after local-context review and exact
  probes.

Hard skip rules:

- if uncertain between `skip_candidate` and `light`, use `light`;
- `skip_candidate` requires `capability_search_required = no`;
- `skip_candidate` requires both likelihood fields to be `none` or `low`;
- do not use `skip_candidate` when local fields, domain, aliases, parent,
  description, matched context, official pages, portfolio/backer pages, or
  trusted databases show any possible crypto/Web3, financial-services,
  investing/fund, trading/execution/liquidity, DeFi, or parent/sub-fund signal.

Capability drift guard:

- The current definitions in this file, `agent_prompt_template.md`, and
  generated worker/verifier instructions are authoritative.
- Workers and verifiers must not copy labels, thresholds, or capability
  boundaries from old final CSVs, old audit reports, repair files, historical
  branch folders, or memory from previous Part6 runs.
- If old outputs conflict with the current definitions, follow the current
  definitions and document the reason in `evidence_summary` or verifier
  feedback.

## Output Schema

Classifier CSV header:

```csv
task_index,investor_id,investor_name,normalized_domain,primary_investor_type,investor_archetype,crypto_native_likelihood,operating_capability_likelihood,search_tier,capability_search_required,risk_flags,classifier_reason
```

Result CSV header:

```csv
task_index,investor_id,investor_name,normalized_domain,primary_investor_type,investor_archetype,crypto_native_likelihood,operating_capability_likelihood,search_tier,capability_search_required,capability_search_reason,status,completed_at,capability_labels,otc_trading,algorithm_trading,market_making,execution_services,defi,sub_fund,other_flags,evidence_urls,evidence_source_types,evidence_summary,confidence,needs_manual_review
```

Schema rules:

- `risk_flags`, `other_flags`, and `capability_labels` must be JSON list
  strings.
- `capability_labels` must exactly equal the list of capability columns whose
  value is `yes`.
- All six capability columns must be `yes` or `no`.
- `status` must be `completed` for completed rows.
- `completed_at` must be a literal ISO-8601 timestamp. Never write shell syntax
  such as `$(date -u ...)`.
- `evidence_urls` must use `|`-separated absolute HTTP(S) URLs.
- `evidence_source_types` must use `|`-separated lowercase source labels such
  as `official_site`, `official_docs`, `official_filing`,
  `official_blog_or_press`, `trusted_database`, `secondary_profile`,
  `ordinary_news_context`, or `local_csv`.
- `ordinary_news_context` and `local_csv` cannot directly support a capability
  `yes`.
- For no-search skip rows, leave `evidence_urls` and `evidence_source_types`
  blank instead of writing `[]`.
- For searched rows, `evidence_urls` and `evidence_source_types` must be
  non-empty unless the identity/current entity cannot be resolved after real
  search. That narrow exception requires all capabilities `no`,
  `confidence = low`, `needs_manual_review = yes`, and an `other_flags` marker
  such as `identity_unresolved` or `no_reliable_external_match`.
- `evidence_summary` must be non-empty for every result row.
- `confidence` must be `high`, `medium`, or `low`.
- `needs_manual_review` must be `yes` or `no`.

Allowed `investor_archetype` values:

- `traditional_vc_or_pe`
- `crypto_native_vc`
- `hedge_fund_or_quant`
- `market_maker_or_otc_firm`
- `asset_manager_or_family_office`
- `accelerator_or_incubator`
- `angel_or_individual`
- `exchange_affiliated_investor`
- `operating_company_disguised_as_investor`
- `fund_vehicle_or_fund_platform`
- `unclear`

Allowed likelihood values:

- `high`
- `medium`
- `low`
- `none`
- `unclear`

## Capability Definitions

Global attribution rule:

- A parent row can inherit a controlled subsidiary, controlled operating unit,
  controlled brand/platform, or official group entity capability when current
  sources show the relationship.
- A child, venture arm, fund, subsidiary, individual, portfolio company,
  minority investment, LP investment, partner, ecosystem member, client, or
  service provider does not inherit parent or affiliate capabilities unless the
  row itself has current capability evidence.
- For individuals, do not infer capability from founder, advisor, executive,
  employee, investor, token-holder, or affiliation status.
- Set `needs_manual_review = yes` after one extra disambiguation pass when
  identity, current status, parent/control relationship, official-vs-database
  conflict, self-operated-vs-third-party service, or source attribution remains
  unclear.

`otc_trading = yes`:

- Current operating-capability label.
- Mark `yes` only when current official/trusted evidence shows that the
  investor itself currently provides OTC trading service, or a parent row
  inherits a controlled child/unit OTC service.
- Includes OTC desk, over-the-counter trading, block trading, off-exchange
  trading, bilateral trading, bilateral liquidity, institutional OTC,
  dealer-to-client OTC, and centralized dealer/broker/counterparty RFQ.
- Crypto and traditional finance both qualify, including OTC equities, OTC
  derivatives, FX OTC, fixed-income OTC, commodities OTC, bilateral options,
  and swaps.
- Hard negatives: portfolio exposure, investment in an OTC company,
  broker-dealer status alone, market-maker status alone, liquidity-provider
  language alone, OTC access/connection to third-party counterparties,
  settlement/custody/post-trade-only support, DEX RFQ, on-chain RFQ/intent,
  on-chain block trade, historical/stopped service, and individual association.

`algorithm_trading = yes`:

- Current operating-capability label.
- Mark `yes` only when current official/trusted evidence shows that the
  investor itself currently uses, provides, or operates algorithmic,
  quantitative, systematic, HFT/high-frequency, low-latency trading-engine,
  automated trading-strategy, trading-bot, grid-bot, AI-bot, or algorithm
  trading service/agency capability, or a parent row inherits it from a
  controlled child/unit.
- Crypto and traditional finance both qualify.
- Hard negatives: portfolio exposure, market-maker status alone, proprietary
  trading status alone, liquidity-provider language alone, "technology-driven
  trading firm" language alone, sophisticated trading-technology language
  alone, API/FIX/connectivity, low-latency access alone, smart order routing
  alone, TWAP/VWAP alone, routing/execution algorithms alone, brokerage or
  execution-desk products, historical/stopped service, and individual
  association.

`market_making = yes`:

- Current operating-capability label.
- Mark `yes` only when current official/trusted evidence shows that the
  investor itself currently provides market making or liquidity provision using
  its own, proprietary, balance-sheet, or otherwise controlled capital/liquidity,
  or a parent row inherits it from a controlled child/unit.
- Crypto and traditional finance both qualify, including designated market
  maker, official market maker, designated liquidity provider, LP, principal
  liquidity, balance-sheet liquidity, and OTC bilateral/RFQ liquidity roles.
- AMM, DEX, or pool operation qualifies only when the investor itself provides
  LP capital/liquidity. Operating or governing a pool without LP capital is
  `market_making = no`.
- Hard negatives: portfolio exposure, generic liquidity-provider/deep-liquidity
  language, liquidity access, quotes/pricing only, routing/matching/execution
  venue operation, exchange/broker/prime-broker status alone,
  proprietary-trading/HFT/quant status alone, passive fund/LP allocation,
  token/protocol liquidity support that is not the investor's own ongoing
  LP/market-maker role, third-party market-maker allocation, historical/stopped
  service, and individual association.

`execution_services = yes`:

- Current operating-capability label.
- Mark `yes` only when current official/trusted evidence shows that the
  investor itself currently provides or operates trade execution, order
  placement, order handling, executable brokerage, execution venue, matching
  engine, exchange/CEX, ATS/MTF/ECN, agency execution, prime-brokerage
  execution, executable DMA, DEX, swap, perp DEX, AMM, or on-chain trading
  protocol capability, or a parent row inherits it from a controlled child/unit.
- Crypto and traditional finance both qualify.
- Exchange, trading venue, matching engine, CEX, traditional exchange, ATS,
  ECN, MTF, DEX, swap, perp DEX, AMM, and on-chain trading protocol operation
  qualify even if they do not qualify for `market_making`.
- Hard negatives: portfolio exposure, API/FIX/connectivity alone, routing or
  smart order routing alone, liquidity access/aggregation alone, connecting
  users to third-party venues/counterparties/liquidity providers, external
  wallet-to-DEX links, white-label or embedded third-party execution,
  redirect-to-external-venue trading, custody/settlement/clearing/post-trade
  only service, market making alone, OTC desk alone, view-only apps,
  historical/stopped service, and individual association.

`defi = yes`:

- Current DeFi trading / DeFi protocol operation label.
- The core question is whether the investor currently does DeFi trading or
  DeFi operations, not whether it merely has investment exposure to DeFi
  companies.
- Mark `yes` when current official/trusted evidence shows at least one of:
  current operation of a DeFi protocol, product, venue, or service; current
  trading through DeFi protocols; current DEX/AMM/swap trading; perp,
  derivatives, options, RFQ, or intent trading; lending/borrowing/credit use;
  DeFi leverage/collateral activity; vault/yield farming; liquid
  staking/restaking; LP capital deployment; DeFi market making/liquidity
  provision; on-chain arbitrage; MEV; liquidations; managed DeFi strategy; or
  one-way parent inheritance from a controlled child/unit/fund that currently
  does DeFi trading or DeFi protocol operation.
- Operating a DeFi protocol counts as `yes` even without evidence that the
  investor uses its own capital to trade on that protocol.
- Hard negatives: crypto/Web3 name or thesis alone, DeFi portfolio exposure,
  token investment, SAFT, grant, accelerator support, ecosystem funding,
  DeFi-adjacent infrastructure exposure, oracle/bridge/L1/L2/wallet/custody
  operation without DeFi financial protocol operation, CEX/broker customer
  DeFi access where customers trade, secondary-market token holding,
  historical/stopped/pivoted/bankrupt DeFi activity, and individual association
  without explicit personal DeFi operation/trading evidence.

`sub_fund = yes`:

- Current structure / attribution label, not an operating-capability label.
- Judge from the current investor row as the parent/mother entity.
- Mark `yes` only when current official/trusted evidence shows that the current
  investor currently owns, controls, contains, or has under it a sub-fund, fund
  vehicle, venture arm, investment arm, crypto arm, dedicated capital pool,
  dedicated investment/trading branch, or comparable sub-fund-like structure.
- Traditional structures can qualify, including sub-fund, feeder fund,
  master-feeder, umbrella fund compartment, parallel fund, SPV, segregated
  portfolio, protected cell, fund platform, and fund-of-funds vehicle.
- Broad operating-company, proprietary-trading, and CVC structures can qualify
  when sources show the parent/child relationship and dedicated
  investment/trading/capital mandate.
- Hard negatives: the row itself is merely a fund vehicle, feeder, SPV,
  protected cell, venture arm, investment arm, crypto arm, subsidiary, brand,
  business unit, accelerator, incubator, ecosystem program, portfolio company,
  ordinary CVC type, externally managed fund, generic manager, ordinary closed
  fund, `LastClosedFundName`, `PrimaryInvestorType`, name-only Ventures /
  Capital / Labs / Crypto Fund / Fund I / SPV terms, or historical/stopped
  structures.

## Verifier Workflow

Verification is independent from worker classification. A verifier must review
completed queue groups and detect both false positives and false negatives.

Verifier checks must include:

- missing valid capabilities;
- extra invalid capabilities;
- wrong identity or wrong parent/control attribution;
- stale, historical-only, bankrupt, stopped, pivoted, or discontinued evidence;
- official-vs-database conflicts;
- portfolio exposure incorrectly treated as operating capability;
- DeFi investment/support exposure incorrectly treated as DeFi operation;
- sub-fund child rows incorrectly treated as parent rows;
- skipped rows that should have been searched;
- invalid JSON list fields, invalid enums, bad search tier, bad evidence
  source types, and missing evidence summaries.

Verifier CSV header:

```csv
task_index,investor_id,investor_name,classifier_search_tier,worker_capability_labels,verifier_search_tier,verifier_capability_labels,verdict,error_type,error_reason,evidence_urls,recommended_action,corrected_result_row_json
```

Allowed `verdict` values:

- `pass`
- `suspected_missing_capability`
- `suspected_extra_capability`
- `wrong_archetype_or_mapping`
- `search_tier_too_conservative`
- `search_should_not_have_been_skipped`
- `insufficient_evidence`

Hard schema rule: do not use any other verdict token. In particular,
`fail`, `failed`, `error`, `needs_fix`, and free-text verdicts are invalid
and will stop collection at the verifier gate. If the worker row needs an
edit, choose the closest allowed non-pass verdict above and set
`recommended_action = edit_row`.

Allowed `recommended_action` values:

- `accept_worker_row`
- `edit_row`
- `mark_manual_review`
- `rerun_investor`
- `rerun_batch`
- `update_prompt_or_process`

If `recommended_action = edit_row`, `corrected_result_row_json` must be a full
JSON object using the exact `results.csv` schema.

If a searched worker row found no reliable current official/trusted source and
all capabilities are `no`, do not use `rerun_investor` only because evidence
fields are blank. Use `mark_manual_review` or `edit_row` so the row has
`confidence = low`, `needs_manual_review = yes`, and an `other_flags` marker
such as `identity_unresolved` or `no_reliable_external_match`.

## Runtime Workflow

Build formal bridge input when source data changes:

```bash
python3 part5_to_part6/scripts/1_build_part6_investor_input.py
python3 part6_analyse_investor_capabilities/scripts/1_build_investor_capability_batches.py \
  --input-csv part5_to_part6/output/part6_investor_input.csv \
  --output-dir part5_to_part6/output/part6_batches
python3 part5_to_part6/scripts/2_verify_formal_bridge_outputs.py
```

Prepare worker runs:

```bash
python3 part6_analyse_investor_capabilities/scripts/2_prepare_worker_runs.py \
  --batch-dir part5_to_part6/output/part6_batches \
  --runs-dir part6_analyse_investor_capabilities/agent_runs/crypto_investor_parallel \
  --workers 8
```

Run queue-mode supervisor only:

```bash
python3 part6_analyse_investor_capabilities/scripts/6_start_long_running_supervisor.py \
  --batch-dir part5_to_part6/output/part6_batches \
  --final-dir part6_analyse_investor_capabilities/agent_runs/crypto_investor \
  --workers 8 \
  --foreground
```

Part6 is queue-only. Do not use round-mode scheduling as an active run mode.
`round_index` may remain as a queue-group identifier for schedule grouping and
verifier filenames, but it is not a progress metric.

Status checks must use:

```bash
python3 part6_analyse_investor_capabilities/scripts/7_check_longrun_status.py
```

Each status check must report heartbeat age, active workers,
waiting/tail_retry/collect/deferred counts, and current running batch row
progress.

Runtime writes to `schedule.csv` must go through
`part6_analyse_investor_capabilities/scripts/part6_schedule_io.py`.

Completion requires this full verification gate:

```bash
python3 part5_to_part6/scripts/2_verify_formal_bridge_outputs.py \
  --part6-reference-results-csv part6_analyse_investor_capabilities/agent_runs/crypto_investor/results.csv

python3 part6_analyse_investor_capabilities/scripts/3_collect_results.py \
  --lint-only \
  --repair-identity-drift-in-place \
  --fail-on-identity-drift

python3 part6_analyse_investor_capabilities/scripts/10_validate_final_outputs.py \
  --batch-dir part5_to_part6/output/part6_batches \
  --final-dir part6_analyse_investor_capabilities/agent_runs/crypto_investor \
  --expected-row-count 10353
```

The final validator must confirm row count, `task_index` sequence, input order,
classifier/results one-to-one alignment, JSON list fields, no shell literals,
no stale placeholders, and no deterministic skip-rule violations.
